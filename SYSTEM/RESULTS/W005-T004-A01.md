## 3. Key findings

### F1 — Authentication is not tenant isolation

A valid identity/session only establishes a principal. Tenant isolation requires application authorization on the current resource plus an independent data-plane boundary. Client-supplied `organization_id`, `workspace_id`, user IDs or roles cannot be accepted as authorization facts.

**Evidence:** OAuth/OIDC standards + OWASP authorization guidance + multi-tenant architecture guidance.

**Decision state:** security invariant; vendor remains open.

### F2 — Keep external identity separate from application resource identity

Map external identities using stable `(issuer, subject)` to an internal `user_id`; do not make email the resource-ownership key. Keep organizations/workspaces/memberships/permissions in application-owned storage so an identity-provider migration does not rewrite tenant/resource ownership.

Enterprise IdP group/role claims may synchronize application memberships, but cannot bypass application authorization.

**Decision state:** candidate architecture, HIGH confidence.

### F3 — No identity vendor is defensibly preferred yet

Managed B2B identity (WorkOS/Clerk/Auth0 class), self-hosted Keycloak and integrated-platform auth are credible but differ in operations, pricing, SSO/SCIM packaging and lock-in. Missing facts — Suno IdP, SSO/SCIM needs, user/org counts, procurement/data-residency policy, ops ownership — materially affect the choice.

**Decision:** `NO_VENDOR_PREFERENCE`.

### F4 — Pooled relational storage + explicit tenant keys + RLS is the strongest current default candidate, not a locked production choice

Given unknown tenant scale, a pooled relational model minimizes early operational fragmentation. Security requires two independent layers:

1. application authorization/resource ownership checks; and
2. database tenant policy/RLS or equivalent defense-in-depth.

The schema should make tenant identity first-class and prevent cross-tenant references structurally where practical. A bridge/silo escape hatch should allow selected tenants to move to stronger isolation without changing application resource IDs.

**Decision:** `CANDIDATE / PENDING_IMPLEMENTATION_BAKEOFF`; no database/provider preference.

### F5 — PostgreSQL RLS carries concrete role and patch-level gates

If PostgreSQL is selected, runtime roles must not be superuser, table owner or `BYPASSRLS`; private tables require explicit RLS policy coverage and missing tenant context must fail closed. PostgreSQL documents referential-integrity/covert-channel and policy-race considerations, so RLS is not treated as a complete authorization system.

Current security evidence adds a specific release gate: CVE-2026-14666, published 2026-08-13, affected row-security caching before PostgreSQL 18.6 / 17.11 / 16.15 / 15.19 / 14.24. A production deployment using an affected major version must be at or above its fixed patch level.

### F6 — Production must remove arbitrary server filesystem path input

User input may identify a document logically, but may not specify a server filesystem path. Private PDF bytes should use controlled object storage with server-generated opaque keys bound to organization/workspace/document metadata.

**Decision:** hard architecture requirement derived from PROD-004/RISK-0032.

### F7 — PDF ingestion needs a quarantine state machine

Candidate flow:

`AUTHZ UPLOAD INTENT → PRIVATE QUARANTINE → TYPE/STRUCTURE/SIZE/HASH + SANDBOX/AV/CDR AS APPROPRIATE → CLEAN PROMOTION → WORKFLOW`

No document may reach parser/workflow before successful validation. Original filename is display metadata, not storage identity. Source hash/object version is immutable provenance. Exact size/page/scan limits remain pending workload evidence.

**Decision:** candidate lifecycle, HIGH confidence; storage/scanner provider remains open.

### F8 — Signed object grants are bearer capabilities

Presigned URLs/SAS/session URIs must be scoped to an exact object/method and kept short-lived. They must not appear in logs/traces/analytics. Every grant is minted only after current application authorization. API streaming remains a valid alternative for especially sensitive delivery.

### F9 — Least privilege requires separate human/service identities

Recommended privilege separation:

- DB migrator ≠ API runtime ≠ worker runtime ≠ backup operator;
- scanner can read quarantine and write validation state/clean area, but cannot administer tenants;
- CI/deployer does not receive routine document-read access;
- observability exporter receives metadata by default, not raw private content;
- break-glass access is exceptional and audited.

### F10 — Telemetry must not become a shadow content store

Default logs/traces exclude raw PDF text, document-bearing prompts/outputs, tokens, session IDs, signed URL/SAS query strings, secrets and connection strings. Prefer opaque org/workspace/document/run IDs, source hashes, version/config IDs, metrics and classified errors.

### F11 — Retention duration cannot be invented

LGPD arts. 15–16 support purpose/necessity-driven treatment termination and elimination subject to legal exceptions, but this task has no authoritative Suno retention policy. The architecture should model `retention_class`, expiry, legal hold and deletion orchestration, while the actual calendar remains `PENDING_POLICY`.
