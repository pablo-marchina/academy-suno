### Same-run multi-replica safety gap

Two separate RunStore connections loaded the same initial state for one run, appended different replica marks, and then both successfully checkpointed. Sequences 2 and 3 were allocated, but the final whole-run state contained only one mark.

`lost_update_observed = true`.

This isolates the current production blocker: SQLite transaction serialization protects sequence allocation, but `SQLiteRunStore` has no compare-and-swap/version ownership check or per-run lease. A stale replica can therefore overwrite newer whole-run JSON state without rejection.

The finding is an application-level RunStore contract gap, not a claim that SQLite cannot support concurrent writers.

## Candidate research findings

The DR record evaluates four alternatives without a synthetic aggregate score:

1. mandatory baseline: custom async graph + SQLite RunStore;
2. LangGraph;
3. DBOS;
4. Temporal.

Primary documentation establishes that:

- LangGraph has first-class checkpointers/fault-tolerant persistence and documents Postgres as a persistent production option while SQLite is local-file development storage;
- DBOS provides Postgres-backed durable workflows/queues, distributed recovery coordination, and documented conflicting-execution handling at durable boundaries;
- Temporal provides a service/worker/task-queue durable workflow model with declarative Activity retry; non-deterministic/API/LLM work belongs in Activities while Workflow code remains deterministic.

None of those candidate runtimes was installed or executed in the pinned shared foundation gate. Their workload-specific latency, checkpoint write cost, 9-way semantics, and migration burden therefore remain unmeasured rather than inferred from vendor claims.

## Decision

`PENDING_EVIDENCE`.

The current SQLite-backed baseline must **not** be locked as the production multi-replica runtime because the same-run stale-write hard requirement failed. LangGraph, DBOS, and Temporal also must **not** be locked from documentation alone because no candidate has yet passed an identical Academy Suno runtime harness under a production-capable shared state topology.

The current `AsyncGraphOrchestrator` remains the behavioral control/reference implementation while the framework-level production choice stays open.

## Reversal / closure conditions

The decision can advance only after a follow-up common-harness experiment:

- pins exact candidate runtime versions;
- implements minimal Academy adapters for at least LangGraph and DBOS, with Temporal included if a lower-burden candidate does not already satisfy the production hypothesis;
- executes against a production-capable shared state backend/topology;
- repeats exact 9-way, transport-vs-quality, crash/restart, and same-run multi-worker probes;
- records p50/p95, state writes/checkpoints, failure outcomes, and setup/operational burden;
- preserves every existing hard gate with no relaxation.

A custom-baseline path can re-enter production consideration if it adds explicit same-run ownership/CAS semantics on a production shared backend and passes the same multi-worker probes.

## Migration implications

Any future runtime must preserve externally auditable semantics for `run_id`, branch `job_id`, branch-local quality repair, transport retry, `REVIEW_REQUIRED`, exact keyed nine-result join, and terminal history. A framework migration must not collapse quality repair into infrastructure retry or weaken the 9/9 hard gate.

Temporal additionally requires a workflow/activity split around failure-prone LLM/provider calls; DBOS requires workflow/step durability mapping; LangGraph requires mapping the current explicit RunState and fan-in invariants to checkpoint/reducer semantics.
