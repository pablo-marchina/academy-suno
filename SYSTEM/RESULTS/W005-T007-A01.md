## Core architecture finding

The Live Evidence Cockpit must not use a sampled observability backend as its authoritative run-state source.

```text
workflow transaction
  ├─ durable run state
  ├─ durable ordered product/domain events → authorized live snapshot/replay → cockpit
  └─ correlated OTel traces/metrics/logs → collector → backend candidate(s)
```

This directly controls RISK-0035: a trace may be sampled, delayed or unavailable without silently turning the frontend into stale/synthetic evidence.

## Safe telemetry policy

`OUTCOME: CANDIDATE_FOR_T010_LOCK`

Default posture:

- raw source document text: **not emitted**;
- prompts/model inputs: **not emitted**;
- model outputs/repaired content: **not emitted**;
- API keys/tokens/cookies/passwords/secrets: **never emitted**;
- bounded operational metadata: allowed;
- opaque high-cardinality IDs: trace/log/event correlation only under access controls, not metric labels;
- external SaaS export: pseudonymize tenant/workspace/document identifiers when direct identity is not operationally necessary;
- exceptional sensitive debugging: explicit opt-in, tenant/run scoped, audited, redacted/truncated, retention declared by policy and never containing credentials.

This is aligned with current OpenTelemetry GenAI guidance that input/output message attributes may contain PII/sensitive data.

## Live event contract

The event schema is transport-neutral and coordinates with W005-T002's current SSE decision.

- tenant/workspace/document/request/run/job/attempt/branch IDs as applicable;
- trace/span correlation;
- `run_revision`;
- stage/status;
- already-authorized/redacted payload;

Required semantics:

- detect regressive/stale run revisions;

- server-side authorization before serialization;
- no raw filesystem path, credential or unrestricted content in events;
- product path continues safely through telemetry-export outage.

## Metrics / cardinality

Candidate metrics cover:

- run/branch/provider/eval durations;
- p50/p95/p99 through backend histogram queries;
- token/cost observations with pricing provenance;
- eval outcomes and repair count/rate;
- queue depth/wait;
- retries;
- live delivery lag/reconnect/replay;
- collector/export failure/drop signals;
- redaction counts;
- authorization denials;
- 3×3 branch completion.

High-cardinality IDs are explicitly forbidden as default metric labels:

- tenant/workspace/request/run/job/document/trace/span identifiers.

OpenTelemetry's documented SDK default cardinality limit is 2,000 unique attribute combinations per metric stream when not otherwise configured. The task-local illustrative scenario reached 108,000 combinations, demonstrating why this guardrail must be explicit.
