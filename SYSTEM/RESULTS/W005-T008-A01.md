## Proposed load/failure/recovery benchmark

Primary artifact: `docs/production/reliability/W005_T008_LOAD_FAILURE_RECOVERY_PLAN.md`

### Load stages

- `L0_VALIDATE` — single-run harness/telemetry validation;
- `L1_BASELINE` — repeated low-load baseline;
- `L2_CONCURRENCY_LADDER` — closed-model increasing concurrency;
- `L3_ARRIVAL_STAIRCASE` — open-model increasing offered rate;
- `L4_BURST` — bounded impulse above stable load;
- `L5_SOAK` — extended operation below saturation;
- `L6_CONTROLLED_SATURATION` — controlled crossing of the stable region;
- `L7_POST_RECOVERY` — return to reference load and compare behavior.

### Required measurements

Where applicable, every stage records:

- p50/p95/p99 API latency, queue wait and logical run duration;
- offered, admitted and completed throughput separately;
- dropped/rejected work;
- error, retry, timeout and cancellation rates;
- queue depth and oldest-work age;
- CPU/memory and runtime/container saturation signals;
- database pool/connections/wait symptoms;
- worker utilization/concurrency;
- provider 429/5xx/timeout/latency behavior;
- replica counts and scaling events;
- observed cost/idle cost/cost per completed logical run where available;
- accepted/lost/duplicate branch counts and provenance gaps;
- measured recovery behavior.

### Saturation result

Do not report an arbitrary capacity claim. Report:

`SATURATION_INTERVAL = [highest observed stable offered load, first observed unstable offered load]`

with workload profile, environment, dominant bottleneck, repeated/raw observations and uncertainty.

A step is unstable when throughput ceases to track rising offered load while queue/tail latency grows without recovery, a hard downstream/resource limit is reached, retry/drop behavior destabilizes, or a correctness hard gate fails. T009 may refine statistical change-point/CI rules.

### Failure matrix

Defined scenarios include:

- API replica/process loss;
- worker kill mid-run;
- durable database outage;
- queue/broker outage where present;
- object/source-store outage;
- provider 429/5xx/timeout/high latency;
- telemetry export/backend failure;
- rolling deploy/restart;
- schema migration rehearsal/failure path;
- complete application restart/resume;
- backup restore into a clean production-equivalent environment.

Each scenario has a predeclared correctness invariant and binary PASS/FAIL in addition to timing metrics.

## Target deployment invariants

The following are proposed as cross-candidate constraints for T010 synthesis:

1. **Replaceable API tier** — accepted run state cannot depend on one API process/container.
2. **Long-work lifetime decoupling** — long AI/document execution cannot depend on the initiating HTTP request lifetime.
3. **Independent API/worker capacity** — asynchronous work demand should be observable through backlog/age or equivalent signals, not assumed from CPU alone.
4. **Idempotent work identity** — stable run/job IDs and attempt/retry provenance; duplicate delivery cannot create duplicate accepted logical results.
5. **Explicit backpressure** — bounded in-flight work/retries plus admission/rejection/defer behavior and downstream concurrency limits.
6. **Distinct health semantics** — startup, readiness and liveness are separate; overload alone must not create restart storms.
7. **Bounded scaling** — replica/per-replica concurrency caps derive from measured downstream constraints; unbounded autoscaling is prohibited.
8. **Shared durable state** — local SQLite/filesystem are development/baseline mechanisms unless a later DRG changes the production scope.
9. **Controlled migrations** — one-shot migration ownership and cross-version compatibility or explicitly serialized deployment.
10. **Reproducible deployment** — declarative config, secrets outside code, build/image/version provenance.
11. **Restore proof** — backup alone is not recovery evidence; clean restore and application validation are required.
12. **Single real product path** — local/mechanics-only success cannot be promoted to production reliability evidence.
