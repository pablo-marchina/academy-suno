## 3. Objective and implementation

B06 is now represented by a framework-neutral, inspectable graph/state runtime rather than a sequential script hidden behind async calls.

### 3.1 Explicit graph and state machine

`src/suno_content/orchestration/models.py` defines:

- inspectable `GraphDefinition`, `NodeSpec` and `EdgeSpec`;
- explicit run phases: `CREATED -> PLANNED -> BRANCHES_RUNNING -> BRANCHES_COMPLETE -> JOINED -> AGGREGATED -> COMPLETE`, with `REVIEW_REQUIRED` / `FAILED` terminals;
- explicit branch phases: `PLANNED -> GENERATED -> NEEDS_REPAIR -> REPAIRED -> ACCEPTED`, plus review/fail terminals;
- explicit quality actions: `PASS`, `REPAIR`, `REVIEW_REQUIRED`, `FAIL`;
- serialized `RunState` / `BranchState`, including outputs, evaluation, quality-repair count, transport-retry count, events and errors.

The default graph exposes these nodes:

`source -> plan -> branch.generate -> branch.evaluate -> [branch.repair -> branch.evaluate]* -> join -> aggregate -> complete`.

The repair edge is conditional on the evaluator decision, and the join edge requires all nine branches accepted.

### 3.2 Plain-async provisional runtime

`AsyncGraphOrchestrator` implements the graph using `asyncio.gather` for branch fan-out while keeping graph definition/state independent from framework identity.

The planner is required to return **exactly nine jobs**. Job IDs are validated before insertion; a duplicate is a hard `OrchestrationInvariantError`, so dict assignment cannot silently overwrite a branch.

The join is also defensive: it accepts exactly nine accepted branches, requires an output for every branch, rejects duplicate keys and asserts equality between branch keys and joined-output keys.

### 3.3 Persistent RunStore

`src/suno_content/runstore/sqlite.py` implements a durable standard-library SQLite proof backend with:

- latest run state in `run_state`;
- append-only state snapshots in `run_history`;
- monotonically increasing sequence number;
- checkpoint reason and UTC timestamp;
- JSON-serialized state;
- reopen/load/history across independent `SQLiteRunStore` instances;
- transaction protection (`BEGIN IMMEDIATE`) around sequence/checkpoint updates;
- duplicate run-id protection.

Persistence semantics are the intended invariant. SQLite is a proof implementation, not a proposed permanent production-backend lock.

### 3.4 Resume semantics

`start(...)` persists source capture before graph advancement. `resume(run_id)` reloads the latest serialized state from durable storage and validates graph-version compatibility before advancing.

Already accepted branch states are terminal and are skipped on resume. The runtime demo explicitly stops after all branches complete, reopens the SQLite file through a new store/orchestrator instance, then resumes through join/aggregate/complete without regenerating or repairing accepted branches.

### 3.5 Branch-local quality repair

Quality repair is evaluator-driven and state-local. A failing branch transitions to `NEEDS_REPAIR`; only that branch invokes the repair callback, then re-enters evaluation. Accepted siblings are never reopened by another branch's repair.

Repair attempts have an independent limit (`max_quality_repairs`). Exhaustion becomes a quality failure rather than being conflated with network/provider transport behavior.

### 3.6 Transport retry is separate from quality repair

Transport failures are handled only around transport-like generation/repair calls and only for configured exception classes (default `TimeoutError`, `ConnectionError`). They produce:

- `transport_retry` events;
- per-stage `transport_retries` counters;
- independent `transport_retry_limit` exhaustion semantics.

Quality repair produces separate `quality_repair_requested`, `quality_repair` and quality-exhaustion events/counters. Tests deliberately place a transport timeout on one branch and a quality repair on a different branch to prove the two mechanisms cannot masquerade as each other.

## 6. Findings / evidence

### F-001 — REQ-002 can be satisfied without framework lock-in

An explicit graph/state representation does not require LangGraph. The provisional plain-async leader can expose inspectable nodes, edges, conditions, run phases, branch phases and durable transitions while keeping the runtime replaceable.

### F-002 — keyed fan-out/join is now an executable invariant

Branch identity is immutable by `job_id`; the planner rejects duplicates before state insertion and the join validates all nine keys. Silent last-write-wins state loss is converted into a hard failure.

### F-003 — recovery/history moved from memory proof to durable evidence

W002 proved checkpoint/resume semantics in memory. This attempt persists latest state and append-only history in SQLite and demonstrates reopen/resume using a new store/orchestrator instance.

### F-004 — transport reliability and content-quality repair are orthogonal control loops

They now have distinct triggering conditions, counters, events, limits and failure semantics. A provider timeout cannot consume a quality-repair attempt, and a quality failure cannot be mislabeled a transport retry.

### F-005 — targeted repair preserves accepted work

Only branches explicitly routed by `EvaluationAction.REPAIR` invoke repair. The persistent resume test proves previously accepted branches remain untouched across restart as well as across sibling repairs.

### F-006 — LangGraph still lacks promotion evidence in this environment

The unchanged challenger remains unavailable because the dependency is absent. This preserves the evidence-based architecture posture rather than promoting a framework from preference.

## 9. Assumptions / risks affected

### A-0005 / LangGraph component

**Remain `PENDING_RUNTIME_RECHECK`.** There is still no executed evidence in this environment that justifies promoting LangGraph over the plain-async leader.

### Persistence backend

**Do not lock SQLite as the production backend from this result.** The task proves a persistence contract and restart behavior using a low-complexity standard-library implementation. T007 telemetry and later deployment requirements should determine whether synchronous SQLite is sufficient or should be replaced behind the same RunStore boundary.

### Concurrency / throughput

The runtime intentionally favors correctness/auditability. SQLite checkpoint writes are synchronous and frequent by design for the proof. Production concurrency, lock contention, disk latency and checkpoint compaction are still unknown and should be measured rather than inferred.

### JSON persistence boundary

Run state must remain JSON-serializable at the RunStore boundary. Provider SDK objects or opaque runtime handles must be normalized before entering persisted state.

### Crash granularity

The runtime checkpoints material graph transitions and transport retry events. Exactly-once external side effects are not claimed; provider adapters should use idempotency keys/job identity if external calls can be duplicated by process failure between external completion and local checkpoint.
