## 3. Objective and implementation

B09 is implemented as a bounded, diagnostic targeted-repair layer under `src/suno_content/repair/**`. It composes accepted evaluator outputs rather than modifying accepted grounding/orchestration/audience packages.

### 3.1 Repair request is diagnostic, not generic reflection

`build_repair_request(...)` converts concrete failure codes and violated local metrics into typed `RepairDirective`s. Examples:

- `SOURCE_*` → `RESTORE_SOURCE_LINEAGE`;
- `FACTUAL_*` → `CORRECT_FACTUAL_CLAIM_FROM_SOURCE`;
- `POLICY_*` → `REMOVE_OR_REFRAME_POLICY_VIOLATION`;
- `CLAIM_CONTRADICTED*` / `CLAIM_UNSUPPORTED*` → claim-local rewrites;
- `REQUIRED_CONCEPT_OMISSION` / low `required_concept_recall` → `RESTORE_REQUIRED_CONCEPTS`;
- `UNEXPLAINED_JARGON` → `EXPLAIN_FIRST_USE`;
- contextualization/analogy findings → local audience adaptation;
- anti-gaming codes → targeted cleanup without deleting required concepts.

`RETRIEVAL_MISS` and `EXTRACTION_AMBIGUITY` are explicitly **not** treated as content-rewrite problems. They route to evidence/extraction review and can stop with `NO_LOCAL_REPAIR_AVAILABLE`. Unknown codes also remain non-repairable until mapped; the loop does not invent a generic “reflect and try again” instruction.

### 3.2 Accepted siblings are immutable

`TargetedRepairLoop.run(...)` receives the failed branch separately from `accepted_siblings`. Only a deep copy of the failed output is passed to the repair callback.

Every accepted sibling is SHA-256 hashed before repair and hashed again immediately after the repair callback. Any mutation raises `RepairInvariantError("accepted sibling output mutated during branch-local repair")` before acceptance/re-evaluation can proceed.

This complements W003-T003 branch-local orchestration without reopening or rewriting accepted sibling outputs.

### 3.3 Source/factual/policy hard gates must re-run after every repair

Every `EvaluationSnapshot` contains exactly one hard gate for:

- `SOURCE`;
- `DETERMINISTIC_FACTUAL`;
- `POLICY`.

A snapshot cannot be `PASS` while any hard gate is `FAIL`/`REVIEW_REQUIRED`, and cannot be `PASS` while failure codes remain.

After each repair, the loop requires a **new `run_id` for all three hard-gate authorities**. Reusing any pre-repair gate execution raises `RepairInvariantError`, making “repair then reuse old gate result” invalid by construction.

`src/suno_content/repair/adapters.py` provides `snapshot_from_hybrid_decision(...)`, which consumes the accepted grounding `HybridDecision` via its public fields and requires explicit run IDs for SOURCE/DETERMINISTIC_FACTUAL/POLICY. It preserves hard-gate/finding failure codes while keeping the accepted grounding package immutable.

Soft/audience metric improvement never compensates a surviving factual/policy/source hard fail.

### 3.4 Before/after lineage and measurable deltas

Each repair attempt persists an immutable `RepairAttemptLineage` containing:

- attempt number and `job_id`;
- typed repair request and trigger codes/metrics;
- complete before/after evaluation snapshots;
- before/after output hashes;
- accepted-sibling hashes before/after;
- signed metric deltas respecting `MAXIMIZE` vs `MINIMIZE` direction;
- resolved failure codes;
- newly introduced failure codes;
- hard-gate regressions.

This makes a local repair auditable as a before/after transition rather than a replacement output with lost history.

### 3.5 Explicit bounded stop criteria

The loop has an explicit configurable `max_attempts` (default `2`) and finite terminal reasons:

- `ALREADY_ACCEPTED`;
- `ACCEPTED_AFTER_REEVALUATION`;
- `NO_LOCAL_REPAIR_AVAILABLE`;
- `NO_MEASURABLE_IMPROVEMENT`;
- `HARD_GATE_REGRESSION`;
- `MAX_ATTEMPTS_REACHED`.

There is no unbounded self-reflection/retry loop. Hard-gate regression terminates immediately. With `stop_on_no_improvement=True` (default), a non-passing attempt that resolves no failure, reduces no hard block and improves no tracked metric terminates rather than consuming attempts indefinitely.

## 7. Findings / evidence

### F-001 — A repair request must preserve the evaluator’s diagnostic vocabulary

Failure codes and metric violations are sufficient to choose a local repair operation without asking the generator to perform generic self-critique. Unmapped/evidence-pipeline failures should stop or escalate rather than trigger unconstrained rewriting.

### F-002 — Hard-gate re-evaluation needs execution identity, not only repeated status fields

Checking “factual PASS” twice is insufficient evidence that factual validation actually ran twice. Fresh per-authority `run_id`s turn post-repair re-execution into an auditable invariant.

### F-003 — Sibling immutability is cheaply enforceable at the repair boundary

Before/after hashes convert “repair only the failed branch” from orchestration intent into a runtime invariant. A callback that mutates an accepted sibling is rejected.

### F-004 — Improvement and convergence are different claims

A repair can improve one metric while leaving a policy/factual hard fail unresolved, or can resolve one failure while introducing another. Therefore B09 records signed metric deltas, resolved/new codes and hard-gate regression independently. Only a fully passing re-evaluation is accepted; no convergence claim is derived from partial improvement.

### F-005 — Evidence-pipeline failures are not safely repairable by rewriting content

`RETRIEVAL_MISS` and `EXTRACTION_AMBIGUITY` require evidence/retrieval/extraction intervention. Treating them as prose-quality failures would risk rewriting around missing evidence and increasing RISK-0001.
