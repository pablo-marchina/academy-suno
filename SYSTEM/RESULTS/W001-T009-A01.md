# 3. Resumo executivo

O Hybrid Evaluator recomendado é um **sistema hierárquico, não compensatório e evidence-first**, não uma média de métricas.

A decisão de um output deve seguir esta ordem lógica:

```text
FROZEN SOURCE + PROVENANCE
→ SOURCE EXTRACTION TRUST GATE
→ FACTUAL BACKBONE / REQUIRED CONCEPTS
→ DETERMINISTIC FACTUAL CHECKS
→ CLAIM-LEVEL GROUNDING
→ CONCEPT / TERMINOLOGY FLOORS
→ AUDIENCE COMPLEXITY VECTOR
→ CALIBRATED AUDIENCE CLASSIFIER
→ FORMAT-SLICED DIAGNOSTICS
→ HYBRID DECISION
→ TARGETED REPAIR
→ RE-EVALUATION
```

Princípio central:

> nenhum ganho em legibilidade, densidade de termos, estilo ou classificação de audiência pode compensar corrupção factual, perda de conceito material obrigatório ou violação crítica de grounding.

A arquitetura distingue três classes de sinal:

1. **hard gates não compensáveis** — verdade factual, lineage material, conceitos obrigatórios e violações críticas;
2. **soft/calibrated decision signals** — Audience Complexity Vector, densidade/sofisticação conceitual, contextualização e classificação ordinal de audiência;
3. **diagnostics** — sinais úteis para explicação, debugging, anti-gaming e targeted repair, sem poder isolado de aprovação.

O evaluator não deve produzir apenas `score=87`. Ele deve produzir uma decisão estruturada com gates, vetor de métricas, evidência, incerteza e ações de reparo localizadas.

# 4. Arquitetura do Hybrid Evaluator

## 4.1 Unidade de avaliação

A unidade externa é um `OutputVariant` identificado por:

```text
source_id
output_id
audience_target: BEGINNER | INTERMEDIATE | ADVANCED
format: ARTICLE | CAROUSEL | SHORT_VIDEO
output_text / structured_content
```

A unidade interna factual é o **atomic material claim**.

A unidade interna de terminologia é o **financial concept normalizado**, não a string superficial.

A unidade de calibração experimental é o **documento-fonte**: todas as variantes do mesmo documento pertencem ao mesmo split.

## 4.2 Inputs mínimos

```yaml
HybridEvaluatorInput:
  source_document: SourceDocument
  source_spans: [SourceSpan]
  table_provenance: [TableCellProvenance]
  source_anchor_ledger: [Anchor]
  required_concepts: [RequiredConcept]
  authorized_concepts: [ConceptRef]
  required_technical_labels: [ConceptRef]
  output_variant: OutputVariant
  evaluator_config_version: string
  ontology_version: string
  feature_schema_version: string
  semantic_backend_version: string|null
```

`required_concepts`, `authorized_concepts` e `required_technical_labels` devem ser definidos a partir da fonte/rubrica/política **antes** de avaliar o output. O próprio output não pode decidir o que era obrigatório preservar.

## 4.3 Pipeline lógico

### Stage A — Source trust

Objetivo: impedir que uma extração ruim se torne “verdade” para o restante do sistema.

Entradas:
- parser/version;
- source hash;
- página/bbox/section/table metadata;
- sinais de OCR, leitura, tabela e divergência entre parsers.

Saída:
- `HIGH | MEDIUM | LOW` por span/anchor, com reasons;
- `source_trust_gate`.

Regra: claim material que dependa exclusivamente de evidência `LOW` para um anchor crítico **não pode receber auto-PASS**.

### Stage B — Deterministic factual anchors

Extrair/normalizar e ligar a papéis semânticos:

- números;
- percentuais;
- p.p. / bps;
- moedas e escalas;
- datas e períodos;
- entidades/tickers;
- métricas financeiras;
- direção/comparadores;
- negação;
- modalidade/condição;
- atribuição.

Checks determinísticos críticos precedem semantic judge.

### Stage C — Atomic claim grounding

1. decompor sentença em claims materiais;
2. exigir coverage de sentenças com anchors materiais;
3. recuperar evidence packet com bias anchor-first;
4. preservar `span_id`, página/bbox e table context;
5. classificar suporte:
   - `SUPPORTED`;
   - `CONTRADICTED`;
   - `UNSUPPORTED`;
   - `AMBIGUOUS`;
   - `UNVERIFIABLE`;
6. usar NLI/alignment/grounding model como sensor semântico calibrável;
7. QA escalation opcional apenas para casos high-risk/ambiguous.

### Stage D — Financial concept / terminology layer

1. match concept-centric com aliases tipados;
2. longest-match-wins para termos nested/multiword;
3. collapse de aliases equivalentes;
4. distinguir `near/related` de equivalência segura;
5. calcular preservação, contextualização e novelty;
6. emitir anti-gaming diagnostics.

### Stage E — Audience Complexity Vector

Calcular vetor linguístico multidimensional:

```text
ACV = {
  surface_readability,
  lexical_accessibility,
  syntactic_complexity,
  cohesion_connectivity,
  domain_concept_signals,
  factual_preservation_context
}
```

Os quatro primeiros blocos vêm de T002; os sinais de domínio e preservação entram como contexto/floors de T003/T004, não como uma simples média.

### Stage F — Calibrated audience decision

Aplicar classificador ordinal/calibrável sobre features permitidas, sem acessar `generation_target_level` como gold.

Saída:

```text
predicted_level
class_scores_or_probabilities (quando backend permitir)
uncertainty
calibration_version
```

Fronteiras, probabilidades e política operacional de aceitação devem ser calibradas em `DEVELOPMENT_GOLD` e congeladas antes do held-out.

### Stage G — Hybrid decision

```text
if source_trust critical fail:
    FAIL / HUMAN_REVIEW
elif factual hard gate fail:
    FAIL
elif concept-preservation hard gate fail:
    FAIL
elif audience decision cannot be trusted:
    REVIEW_REQUIRED
elif predicted audience inconsistent with target under frozen acceptance policy:
    FAIL_AUDIENCE
else:
    PASS
```

A arquitetura não define agora o cutoff numérico de “inconsistent with target”; esse cutoff depende da calibração.

# 5. Hard fails vs soft/calibrated scores vs diagnostics

## 5.1 Hard fails que podem ser congelados como invariantes de desenho

### HF-01 — Unresolved critical factual contradiction

Qualquer finding factual `CRITICAL` não resolvido bloqueia PASS.

Exemplos:
- número material errado;
- escala/unidade errada;
- moeda errada;
- entidade/metric role swap;
- período errado;
- direção invertida;
- negação invertida;
- condição removida;
- possibilidade/estimativa promovida a fato;
- tabela ligada à linha/coluna errada;
- anchor crítico sustentado apenas por extração não confiável.

### HF-02 — Unresolved ERROR em material claim impede auto-PASS

Há uma diferença de ênfase entre os RESULTs:

- T005 fixa explicitamente `CRITICAL` como hard fail mínimo;
- T004 é mais estrito e exige zero `ERROR` não resolvido em material claims para factual PASS automático.

Síntese recomendada sem esconder o conflito:

- `CRITICAL` é hard fail absoluto;
- `ERROR` material não resolvido bloqueia **auto-PASS** e exige repair/re-evaluation ou disposição humana explícita;
- eventual override humano deve ficar auditado, nunca convertido silenciosamente em “supported”.

### HF-03 — Missing required material concept

Se um conceito marcado em `R_f` como material obrigatório desaparecer ou tiver significado material perdido, o output falha independentemente de Flesch/densidade.

Não congelar agora um cutoff genérico de `RCR`. A regra hard é por conceito material obrigatório, não por uma porcentagem inventada.

### HF-04 — Unsupported material domain concept

Novo conceito técnico que altere interpretação factual/regulatória e não esteja autorizado pela fonte/scaffolding deve falhar pela camada de grounding/concept policy.

`UDCR` continua métrica diagnóstica; não congelar cutoff numérico global.

### HF-05 — Beginner: true unexplained required jargon violates the contract

O Case Contract exige “zero jargão financeiro desacompanhado de analogia cotidiana” para Beginner.

Distinção necessária:

- **invariante editorial**: uma violação verdadeira é fail;
- **detector operacional**: threshold/tolerância do detector de `UJR`, definição e analogia deve ser calibrado para não confundir erro de detecção com erro editorial.

Portanto não se fixa agora `UJR <= X` como threshold técnico final.

### HF-06 — Required technical label loss when explicitly designated

Para Advanced, se a rubrica/source policy marcar determinado `concept_id` como `required_technical_label`, sua remoção sistemática é fail de contrato.

Não transformar `TLP` global em cutoff arbitrário antes de gold calibration.

## 5.2 Soft/calibrated decision signals

Devem ser calibrados experimentalmente:

- Flesch PT-BR raw;
- palavras/sentença;
- sílabas/palavra;
- lexical frequency/rarity;
- diversidade lexical robusta a comprimento;
- complexidade sintática;
- coesão/connectivity;
- `UCD`;
- `DWCD`;
- `TLP` quando não há label obrigatório binário;
- `UJR` como detector contínuo;
- Definition/Context/Analogy Coverage;
- semantic support confidence;
- calibrated audience classifier scores/probabilities.

Esses sinais informam `predicted_level`, uncertainty e repair, mas não podem apagar um hard fail factual/conceitual.

## 5.3 Diagnostics sem poder isolado de aprovação

- historical Flesch bands;
- repeated mention share;
- alias stuffing;
- glossary dumping;
- unsupported finance candidates;
- unknown concepts;
- syllable/tokenization coverage;
- parser disagreement;
- low-confidence evidence dependency;
- retrieval miss;
- output length;
- slice metadata;
- model/parser/ontology versions.

# 6. Audience Complexity Vector — composição recomendada

O ACV não deve ser reduzido a uma soma linear não calibrada.

## 6.1 `surface_readability`

```yaml
surface_readability:
  flesch_ptbr_raw: float|null
  words_per_sentence: float|null
  syllables_per_word: float|null
  long_sentence_ratio: float|null
  syllable_coverage: float
  unsupported_tokens: [string]
```

Regras:
- guardar raw score;
- clipping 0–100 é apresentação, não verdade;
- tokenizer/sentence segmenter/syllabifier são versionados;
- siglas, percentuais, moedas, datas, `1T26`, tickers e estrangeirismos têm política explícita;
- outputs curtos carregam uncertainty/coverage.

## 6.2 `lexical_accessibility`

Candidatos:
- frequency/rarity de palavras de conteúdo;
- `simple_word_ratio`;
- length-robust lexical diversity;
- foreign-term share;
- familiaridade/concretude/AoA apenas se houver fonte reproduzível.

Não usar TTR cru como métrica principal entre comprimentos distintos.

## 6.3 `syntactic_complexity`

Candidatos:
- clauses per sentence;
- subordinação/relativas;
- words before main verb;
- dependency distance;
- noun phrase length.

Objetivo: detectar hacks como `sentence_chopping` em que pontuação muda sem simplificação real.

## 6.4 `cohesion_connectivity`

Candidatos:
- referential overlap controlado;
- conectivos causais/aditivos/temporais;
- conexão entre blocos;
- repetition penalty.

Objetivo: evitar que frases curtas e desconexas pareçam “melhores” só por Flesch.

## 6.5 `domain_concept_signals`

```yaml
domain_concept_signals:
  unique_concept_density: float|null
  difficulty_weighted_concept_density: float|null
  required_concept_recall: float|null
  unexplained_jargon_rate: float|null
  definition_coverage: float|null
  context_coverage: float|null
  analogy_coverage: float|null
  technical_lexical_preservation: float|null
  unsupported_domain_concept_rate: float|null
  repeated_mention_share: float|null
```

Esses sinais não entram cegamente numa média; alguns materializam floors binários por concept/claim e outros servem ao classificador de audiência.

## 6.6 Hipótese ordinal a validar

Sem assumir monotonicidade perfeita por peça:

- Beginner tende a linguagem mais acessível, maior explicação/analogia e menor pressuposição de repertório;
- Intermediate ocupa região intermediária com vocabulário padrão de mercado;
- Advanced tolera maior densidade/abstração e exige preservação técnica quando material;
- `RCR` e factuality devem permanecer fortes nos três níveis.

Um Advanced não falha apenas por ter Flesch baixo; um Beginner não passa apenas por Flesch alto.

# 7. Ontologia financeira e matching

## 7.1 Schema mínimo

```yaml
FinancialConcept:
  concept_id: string
  pref_label_pt: string
  aliases:
    - value: string
      relation: exact | acronym | translation | near | deprecated
  definition_canonical: string
  definition_beginner: string|null
  analogy_templates: [string]
  category: string
  subcategory: string|null
  difficulty_prior: 1 | 2 | 3
  audience_policy:
    beginner: string
    intermediate: string
    advanced: string
  document_types: [string]
  source_refs: [SourceRef]
  normative_status:
    status: active | deprecated | future
    valid_from: date|null
    valid_to: date|null
  relations:
    broader: [concept_id]
    narrower: [concept_id]
    related: [concept_id]
  match:
    forms: [string]
    longest_match_priority: true
    context_rules: [Rule]
  requiredness_rules: [Rule]
  verification_tests: [Fixture]
```

## 7.2 Invariantes de matching

Podem ser congelados agora:

- conceito é a unidade, não string;
- aliases equivalentes contam uma vez;
- longest-match-wins;
- `EBITDA ajustado` ≠ `EBITDA`;
- `CDI` ≠ `Taxa DI` como equivalência automática;
- repetitions não elevam UCD/DWCD;
- unknown candidates não recebem bônus automático;
- ontology version é persistida em todo report.

## 7.3 Métricas

### UCD

```text
UCD(y) = 100 * |C(y)| / max(N(y), 1)
```

### DWCD

```text
DWCD(y) = 100 * Σ[c ∈ C(y)] d_c / max(N(y), 1)
```

### RCR

```text
RCR(y) = Σ[c ∈ R_f] w_c * I[preserved(c, y)]
         / Σ[c ∈ R_f] w_c
```

### TLP

```text
TLP(y) = Σ[c ∈ L_f] w_c * I[approved_technical_label(c) appears]
         / Σ[c ∈ L_f] w_c
```

### UJR

```text
UJR(y,a) = Σ[c ∈ E_a] w_c * I[not contextualized_on_first_use(c)]
           / Σ[c ∈ E_a] w_c
```

### UDCR

```text
U(y) = C(y) \ A_s
UDCR(y) = weighted_share_of_unsupported_concepts
```

Os pesos finais, difficulty priors, contextual window e cutoffs operacionais permanecem calibráveis.

# 8. Factuality / grounding architecture

## 8.1 Core invariant

```text
SOURCE
→ provenance-preserving extraction
→ SourceSpan / TableCell ledger
→ generated output
→ atomic material claims
→ deterministic anchor checks
→ evidence retrieval
→ semantic verification
→ severity / gate
→ repair or review
```

## 8.2 Precedência de decisão factual

```text
1. SOURCE EXTRACTION TRUST GATE
2. DETERMINISTIC CRITICAL CONTRADICTIONS
3. DETERMINISTIC SUPPORT/MISMATCH SIGNALS
4. SEMANTIC ENTAILMENT/CONTRADICTION
5. OPTIONAL QA ESCALATION
6. STRUCTURED LLM EXPLANATION/TRIAGE
```

Nenhum modelo semântico pode sobrescrever mismatch crítico determinístico.

## 8.3 Source / claim objects

O mínimo deve preservar:

```yaml
SourceDocument:
  document_id: string
  source_hash: sha256
  source_type: string
  parser_id: string
  parser_version: string
  extraction_status: PASS | REVIEW_REQUIRED | FAIL

SourceSpan:
  span_id: string
  document_id: string
  page: int|null
  bbox: [float]|null
  section_path: [string]
  block_type: string
  text: string
  extraction_method: string
  extraction_confidence: HIGH | MEDIUM | LOW
  source_hash: sha256

Claim:
  claim_id: string
  output_id: string
  sentence_id: string
  text: string
  materiality: MATERIAL | NON_MATERIAL
  modality: ASSERTED | ESTIMATE | EXPECTATION | POSSIBILITY | CONDITIONED | OTHER
  attribution: string|null
  period: string|null
```

## 8.4 Semantic layer

Backend deve ser plugável:
- dedicated grounding verifier;
- NLI;
- alignment model;
- structured LLM verifier como sensor adicional.

Não herdar accuracy/cutoff de paper externo como verdade do projeto. Calibrar no gold financeiro local.

# 10. Targeted repair protocol

## 10.1 Regra

Reparar a menor unidade que resolve a falha, preservando o que já passou.

Exemplos:

### Wrong number/unit

```yaml
required_action: correct_factual_anchor
repair_scope: CLAIM
preserve_constraints:
  - preserve_supported_neighbor_claims
  - preserve_target_audience
  - preserve_format_structure
```

### Missing beginner analogy

```yaml
required_action: add_plain_definition_and_everyday_analogy
repair_scope: CONCEPT
preserve_constraints:
  - do_not_remove_required_concept
  - do_not_change_factual_anchors
```

### Audience too advanced without factual failure

```yaml
required_action: reduce_lexical_and_syntactic_complexity
repair_scope: BLOCK
preserve_constraints:
  - preserve_required_concepts
  - preserve_all_supported_material_claims
  - preserve_numbers_entities_periods_conditions
```

## 10.2 Re-evaluation

Depois do repair:

1. reexecutar checks da dimensão afetada;
2. reexecutar factual hard gates sobre spans alterados;
3. executar regression guard para garantir que repair não quebrou dimensões já aprovadas;
4. registrar before/after metrics + failure IDs resolvidos/novos;
5. respeitar retry cap versionado/calibrado pela arquitetura final.

O valor de `MAX_RETRIES` não é fixado nesta síntese.

# 11. Golden / held-out calibration protocol

## 11.1 Três variáveis que nunca devem ser colapsadas

```text
generation_target_level
human_gold_level
evaluator_predicted_level
```

`generation_target_level` nunca é gold automático.

## 11.2 Dataset MVP recomendado por T005

T005 propõe como MVP defensável:

- 18 documentos;
- 6 COPOM;
- 6 FATO_RELEVANTE;
- 6 RELEASE_RESULTADOS;
- 9 outputs por documento;
- 162 outputs.

Split recomendado:

- 12 documentos development = 108 outputs;
- 6 documentos held-out = 54 outputs;
- 4 development + 2 held-out por família.

**Conflito/nuance com T002:** T002 evita tratar um tamanho fixo como suficiência estatística universal e recomenda ampliar conforme learning curve/instabilidade. Síntese: **18 documentos é um MVP operacional proposto, não prova de suficiência final**. A expansão é obrigatória se CIs/slices forem instáveis.

## 11.3 Split

- split por `source_id`, nunca por output;
- todas as 9 variantes do mesmo documento ficam juntas;
- frozen manifest antes de geração/anotação;
- regra de alocação reproduzível por hash;
- held-out não entra em tuning, prompt design ou error analysis iterativo.

## 11.4 Human gold

Para audience level:

- anotadores cegos ao target/model/evaluator;
- 2 independentes por output no MVP;
- terceiro para adjudicação em desacordo/UNSCORABLE;

# 14. Thresholds/floors: o que congela agora e o que permanece calibrável

## 14.1 Congelar agora como invariantes

1. `CRITICAL factual finding unresolved => FAIL`.
2. `material ERROR unresolved => no auto-PASS`.
3. material claim precisa de source lineage ou deterministic derived trail para auto-PASS.
4. critical anchor não pode depender exclusivamente de low-confidence source extraction.
5. deterministic critical mismatch vence semantic agreement.
6. missing required material concept não é compensável.
7. repetition/alias stuffing não aumenta unique concept density.
8. unsupported material domain concept não recebe bônus e pode acionar factual/policy fail.
9. Beginner tem invariante editorial de não deixar jargão financeiro requerido sem explicação/analogia conforme Case Contract.
10. Advanced preserva technical labels explicitamente designados como required.
11. metrics são fatiadas por formato/source; não comparar densidade bruta cross-format como se fosse equivalente.
12. held-out nunca é tuning set.
13. generation target, human gold e evaluator prediction permanecem separados.

## 14.2 Permanecem calibráveis

Não congelar antes de development gold:

- Flesch bands para BEGINNER/INTERMEDIATE/ADVANCED;
- pesos do ACV;
- fronteiras/classifier thresholds de audiência;
- probability/confidence acceptance threshold;
- difficulty weights `d_c`;
- importance weights `w_c` quando não determinados diretamente pela rubrica/source;
- UCD/DWCD bands;
- UJR detector tolerance;
- Definition/Context/Analogy detection cutoffs;
- TLP global cutoff;
- UDCR cutoff/severity mapping para casos não materiais;
- repetition limits;
- contextualization window ótima;
- semantic NLI/alignment score cutoffs;
- extraction confidence numeric thresholds, se convertidos de reason-based classes;
- retry cap / stop policy;
- eventual weights de qualquer dashboard score secundário.

Qualquer número usado antes da calibração deve ser rotulado `HYPOTHESIS`/`BASELINE`, nunca `FINAL_THRESHOLD`.

# 15. Conflitos e como a síntese os preserva/responde

## C-01 — T005 hard-fail mínimo vs T004 factual PASS mais estrito

- T005: qualquer `CRITICAL` é hard fail.
- T004: zero `CRITICAL` + zero unresolved `ERROR` em material claims para auto-PASS.

Resolução proposta: CRITICAL = fail absoluto; ERROR material = bloqueia auto-PASS até repair/review. Não fingir que os dois RESULTs disseram exatamente a mesma coisa.

## C-02 — Zero Beginner jargon vs detector imperfect

- Case Contract/T003: alvo conceitual verdadeiro é zero jargão financeiro desacompanhado de analogia.
- T003: threshold operacional do detector precisa de calibração.

Resolução: zero é **policy invariant** sobre violação verdadeira; cutoff técnico do detector permanece calibrável.

## C-03 — Dataset size

- T005: 18 documentos como MVP defensável.
- T002: não fixar suficiência estatística por conveniência; ampliar conforme estabilidade.

Resolução: 18 = implementação MVP recomendada; suficiência final depende de CIs, learning curve e slices.

## C-04 — Density vs preservation

- T003 fornece UCD/DWCD.
- T002 alerta que nível não pode ser comprimento/densidade simples.

Resolução: UCD/DWCD são features diagnósticas/calibráveis. RCR/factuality/ACV impedem que densidade vire proxy único.

## C-05 — Semantic judge útil vs risco de circularidade

- T004: NLI/alignment/LLM podem ajudar semantic grounding.
- T005: judge não pode ser gold nem ajustar o held-out.

Resolução: semantic judge é sensor secundário versionado e calibrado contra human/source gold; nunca truth authority.

# 20. Testes mínimos de contrato

## Readability

- empty text returns invalid, not exception;
- exact formula fixture;
- punctuation/markup/URL handling;
- percent/currency/quarter/acronym fixtures;
- unsupported foreign terms emit diagnostic;
- same input + versions => same metrics.

## Ontology

- `EBITDA` == `LAJIDA` concept id;
- `EBITDA ajustado` != `EBITDA`;
- `CDI` != `Taxa DI` exact alias;
- repeated aliases do not increase UCD/DWCD;
- missing required concept reduces RCR and triggers gate when material;
- unrelated finance term increases unsupported signal.

## Factuality

- wrong magnitude;
- scale mismatch;
- p.p. vs percent;
- entity swap;
- negation inversion;
- conditional loss;
- direction inversion;
- period mismatch;
- metric-role mismatch;
- table lineage mismatch;
- modality promotion;
- unsupported causal claim;
- range/comparator contradiction;
- currency mismatch;
- extraction ambiguity veto.

## Integration

- readability improvement + concept deletion => FAIL;
- advanced lexical simplification that removes required technical label => FAIL;
- factual correction repair preserves audience/format;
- audience repair preserves supported claims/anchors;
- fail report contains actionable source/concept/claim refs;
- held-out examples are not loaded by development calibration path.
