## Findings / evidence

### F1 — Adaptive optimization must sit inside a deterministic hard-gate envelope

`HIGH confidence`.

The runtime should separate:

1. candidate eligibility and hard invariants;
2. optimization among eligible routes;
3. post-generation hard-gate acceptance.

Tenant/source/provenance binding, critical factual/policy/schema checks and capability eligibility are never optimizer rewards or penalties: they are constraints. This directly mitigates RISK-0039.

### F2 — Use Pareto/lexicographic decision logic until evidence supports weights

`HIGH confidence`.

Do not invent one scalar score that can hide trade-offs. First require critical gates; then evidence-backed quality/reliability floors; then compare cost, latency and reliability on a Pareto frontier. Exact utility weights remain `PENDING_EVIDENCE`.

### F3 — Start with deterministic rules/cascade; treat learned routing as challenger

`MEDIUM-HIGH confidence`.

Academic evidence supports quality-aware routing/cascades as a viable cost-quality strategy, but published effect sizes are not transferable to Academy Suno. The safest progression is offline → shadow → bounded canary → active, with learned/contextual routing promoted only after representative held-out evidence.

### F4 — Exploration cannot weaken safety or learn directly from circular reward

`HIGH confidence`.

Exploration is allowed only among already eligible routes and all outputs still receive the same post-route hard gates. Automated judge/sensors can guide diagnostics but must not be relabeled as human preference/gold. Any critical hard-gate failure in a canary stops/rolls back that policy version.

### F5 — Retry/fallback requires one bounded end-to-end budget

`HIGH confidence`.

- auth/invalid request/tenant/policy/config incompatibilities fail closed;
- 429/transient 5xx/capacity failures can use bounded retry with `Retry-After` where present plus exponential backoff/jitter;
- timeouts consume the same end-to-end deadline budget;
- fallback only targets capability-equivalent eligible candidates;
- one layer owns retries to prevent multiplicative storms;
- targeted repair is capped and freshly evaluated.

Groq's current Flex documentation explicitly exposes a fast-fail 498 capacity mode, reinforcing the need for typed failure taxonomy rather than generic blind retries.

### F6 — Model/provider IDs, prices and tiers are runtime data, not architecture constants

`HIGH confidence`.

Current OpenAI, Anthropic, Google and Groq catalogs expose materially different models/tier controls, and provider docs show model retirement/price/service-tier drift. Maintain a versioned candidate catalog with lifecycle health and exact price snapshot references. Cost is calculated from observed usage + the versioned official snapshot; estimated and billed cost remain distinct. This controls RISK-0017 and RISK-0019.

### F7 — Telemetry is part of route correctness

`HIGH confidence`.

Every route needs policy/catalog version, candidates considered/rejected, chosen provider/model/tier/config versions, exploration mode, token usage, price snapshot, latency components, retry/fallback chain, provider request ID when available, hard-gate outcomes, repair rounds and final acceptance. OpenTelemetry GenAI conventions are an appropriate base vocabulary, but payload content is redacted/opt-in because prompt/output/system-instruction fields may contain sensitive information.

### F8 — Policy versions must be immutable and rollbackable

`HIGH confidence`.

A policy artifact should contain a semantic version/hash, candidate-catalog snapshot, prompt/retrieval/eval/repair versions, pricing snapshot, rollout mode, experiment reference and pointer to previous known-good. Rollout is atomic; shadow/canary assignments are stable; rollback requires no data migration. Online rewards must not directly mutate/promote the active production policy.
