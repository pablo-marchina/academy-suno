## Decision outcomes

### LOCK

1. **CI platform: GitHub Actions.**
   - Existing native control plane; migration does not solve an evidenced blocker.
   - Supports reusable workflows, dependency caching, OIDC, permissions control, and artifact attestations.

2. **CI hardening/reproducibility policy.**
   - Pin third-party actions to verified full commit SHAs.
   - Use least-privilege `GITHUB_TOKEN` permissions.
   - Require an authoritative committed dependency lock and frozen/locked install behavior once the package manager is selected.
   - Key dependency caches from the lockfile plus relevant runtime/OS dimensions.
   - Restrict cache writes on low-trust triggers.
   - Consolidate repeated setup with repository-local reusable workflows/composite actions after package selection.

3. **Dependency/supply-chain control plane.**
   - Use automated GitHub Actions dependency updates and add package ecosystems after manifests exist.
   - Generate an SBOM for releasable artifacts.
   - Generate and verify GitHub artifact attestations/provenance for release artifacts.
   - Treat SLSA properties as incremental verification targets, not an unverified badge/claim.
   - Add direct Cosign only when a target registry/consumer requires signing semantics beyond GitHub-native attestations.

### PENDING_EVIDENCE

1. **Python package manager.** uv is the lead candidate; Poetry and PDM remain live challengers. Final lock waits for the real dependency/runtime topology and benchmark evidence.
2. **JS package manager/workspace.** pnpm is the lead for a proven multi-package JS/TS workspace; npm is the simplicity baseline for a single package; Yarn remains a challenger. No Node tool is selected before W005-T002 resolves the frontend/API surface.
3. **Repository/build graph.** Keep one repository, but do not add Nx/Turborepo or another task graph until T002/T003 topology and CI measurements show multiple deployables/repeated deterministic work justify the extra layer.

### NO_PREFERENCE

1. **Local environment wrapper.** Native pinned runtimes and Dev Containers are both acceptable behind the same canonical setup/test command contract. Containerization is not mandatory without an evidenced service/native-dependency need.
2. **SBOM encoding.** CycloneDX vs SPDX remains open until a consumer/platform requirement distinguishes them.

## Candidate evidence summary

### Python

- **uv:** lock/sync semantics, workspace support, aggressive caching and explicit GitHub Actions guidance; current lead.
- **Poetry:** mature dependency/project/lock workflow; credible comparator.
- **PDM:** standards-oriented lock metadata including hashes; workspace support exists but current docs mark it experimental.

### JS/workspaces

- **pnpm:** built-in workspaces, shared workspace lock, strict dependency visibility and content-addressed storage. pnpm documents production workspace adoption by major OSS projects such as Next.js, Vite, Vue, SvelteKit, Prisma, Vercel and Turborepo.
- **npm workspaces:** lowest additional tooling and strong single-package/simpler-workspace baseline.
- **Yarn:** mature workspace model and credible alternative where advanced workspace/constraint features matter.

### Build graph

- **Native package scripts + GitHub Actions:** lowest complexity baseline.
- **Nx:** project/task graph and input-hashed caching; strongest heterogeneous-workspace candidate if needed.
- **Turborepo:** focused deterministic task caching and remote cache, strongest when the final topology is JS/TS-centric.

### Local environment

- Native environment, Dev Containers, and Nix-style wrappers were considered. The open Dev Container specification provides a credible repeatable environment without forcing that wrapper today.

### Supply chain

GitHub secure-use guidance states full commit SHA pinning is the immutable action-reference option. GitHub artifact attestations bind provenance to repository/workflow/commit/event metadata and use Sigstore. Dependabot supports version/security updates and grouped update policies. SLSA v1.2 is the current approved specification consulted; provenance/build requirements are used as verification targets. Cosign remains the direct Sigstore signing/verification escalation path.
