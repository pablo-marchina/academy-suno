## EXECUTIVE_SUMMARY

A interface recomendada deve funcionar como um **evidence cockpit**: o usuário começa por uma fonte financeira real, obtém a matriz 3 níveis × 3 formatos e consegue provar, em poucos cliques, quatro coisas separadas: (1) a mesma verdade factual foi preservada, (2) o nível de sofisticação mudou de forma mensurável, (3) o formato realmente mudou de gramática e estrutura, e (4) uma falha detectada produz diagnóstico acionável e repair direcionado até PASS.

A UX não deve esconder hard gates em um score agregado. Cada célula da matriz precisa expor `Audience`, `Format`, `Grounding` e `Policy/critical` como dimensões separadas, com PASS/FAIL explícito. Artigo, Carrossel e Vídeo Curto recebem schemas e evaluators próprios; métricas transversais continuam compartilhadas, mas não substituem o contrato específico de mídia.

O caminho principal da demo cabe em ~4:40, deixando ~20s de reserva sobre a regra operacional de 5:00. O momento central é um caso real `FAIL → diagnostics → targeted repair → PASS`, com diff antes/depois, métricas, source lineage e telemetry visíveis. Fallbacks devem ser transparentes: nunca simular chamada live bem-sucedida; em falha de provider, abrir uma execução persistida/cached claramente rotulada e continuar provando evaluator, source trace e software real.

### 2. Wireflow textual da interface

#### Screen A — `New run / Source`

Objetivo: provar que tudo começa em documento real e rastreável.

Componentes mínimos:
- upload PDF/texto ou seleção de fixture pública reproduzível;
- `source_type` e nome do documento;
- hash/id da fonte e `run_id`;
- preview do documento com páginas/chunks;
- estado de extração: `READY | DEGRADED | BLOCKED`;
- indicadores de anchor coverage/extraction confidence quando disponíveis;
- CTA único: `Generate 3×3`.

Se extração estiver abaixo do piso configurado, a UI deve bloquear geração ou exigir fallback explícito. Isso evita que erro de parsing pareça erro de geração.

#### Screen B — `3×3 Matrix`

Layout recomendado: linhas = audiência (`Iniciante`, `Intermediário`, `Avançado`); colunas = formato (`Artigo`, `Carrossel`, `Vídeo Curto`).

Cada célula mostra:
- preview curto;
- estado global derivado de gates, não média: `PASS | FAIL | REPAIRING | ERROR`;
- badges separados: `Audience`, `Format`, `Grounding` e, se aplicável, `Policy`;
- attempt/retry count;
- latency resumida.

Interações essenciais:
- clicar uma linha compara **mesmo nível entre 3 formatos**;
- clicar uma coluna compara **mesmo formato entre 3 níveis**;
- toggle `Compare audiences` / `Compare formats`;
- filtro `Only failures` para demo e debugging.

#### Screen C — `Output Detail`

Três áreas coordenadas:
1. **Output** — conteúdo formatado conforme a mídia;
2. **Evaluator** — checks, observado, alvo/config, status, evidência e repair hint;
3. **Source** — página/chunk/anchor que sustenta o claim selecionado.

A seleção de uma frase, slide ou segmento deve destacar os source refs correspondentes. Unsupported claim deve ser visualmente um hard fail, nunca apenas reduzir score.

#### Screen D — `Diagnostics + Repair`

Ao FAIL:
- mostrar `failure_code`, dimensão, valor observado, alvo/config, evidência e sugestão de reparo;
- CTA `Repair failed constraints` deve enviar somente constraints falhas + factual backbone, evitando regeneração cega do 3×3 inteiro;
- preservar versão anterior para comparação.

#### Screen E — `Before / After`

Mostrar:
- diff textual/estrutural;
- delta de métricas;
- gates que mudaram de FAIL para PASS;
- factual/source anchors preservados;
- custo/latência adicional do retry;
- link para o run manifest.

### 3. Regra de composição dos evaluators

Não usar uma função única de qualidade para todos os outputs.

Envelope recomendado por célula:

```text
cell_status = PASS only if:
  all critical_grounding_gates PASS
  AND audience_contract PASS
  AND format_contract PASS
  AND mandatory policy/scope gates PASS
```

O score agregado, se existir, é apenas diagnóstico/ordenamento e **não pode compensar hard gate**.

Interface de evaluator proposta:

```text
EvaluatorResult
- evaluator_version
- audience
- format
- hard_gates[]
- checks[]
  - check_id
  - status: PASS | FAIL | WARN
  - observed
  - target_or_config
  - evidence_refs[]
  - failure_code
  - repair_hint
- telemetry
- final_status
```

### 4. Contrato específico — Artigo Analítico

Schema mínimo:

```text
ArticleOutput
- title
- lead_or_summary
- sections[]
  - heading
  - paragraphs[]
  - source_refs[]
- closing_or_takeaways
- source_refs[]
```

Hard/structural checks:
- estrutura de artigo válida; não aceitar dump de slides/timecodes;
- presença de lead e corpo com hierarquia coerente;
- source refs disponíveis para claims factuais relevantes;
- grounding/números/entidades passam gates comuns;
- fechamento/takeaways coerentes com a fonte, sem recomendação nova.

Format-native diagnostics:
- fragmentação excessiva;
- repetição/redundância;
- heading/body mismatch;
- cobertura insuficiente de tópicos selecionados;
- artigo reduzido a bullet dump.

Failure codes sugeridos:
`ARTICLE_SCHEMA_INVALID`, `ARTICLE_FRAGMENTED`, `ARTICLE_TOPIC_GAP`, `ARTICLE_TRACE_MISSING`.

### 5. Contrato específico — Carrossel Informativo

Schema mínimo:

```text
CarouselOutput
- slides[]
  - slide_index
  - role: HOOK | BODY | CONCLUSION
  - headline
  - body
  - visual_cue
  - source_refs[]
```

Hard/structural checks:
- ao menos um hook, corpo e conclusão, em ordem válida;
- cada slide possui uma ideia dominante e source refs para claims;
- nenhum slide depende de parágrafo longo como artigo disfarçado;
- overflow/densidade visual medidos contra configuração calibrável;
- progressão entre slides produz narrativa, não coleção solta de frases;
- grounding comum continua sendo hard gate.

Format-native diagnostics:
- `hook_strength` estruturado;
- `slide_overflow_risk`;
- `ideas_per_slide` / claim density;
- `progression_break`;
- conclusão ausente;
- visual cue ausente onde necessário.

Failure codes sugeridos:
`CAROUSEL_NO_HOOK`, `CAROUSEL_OVERFLOW`, `CAROUSEL_MULTI_IDEA`, `CAROUSEL_NO_CLOSURE`, `CAROUSEL_TRACE_MISSING`.

### 6. Contrato específico — Vídeo Curto

Schema mínimo:

```text
ShortVideoOutput
- segments[]
  - start_s
  - end_s
  - narration
  - on_screen_text
  - visual_cue
  - source_refs[]
- estimated_spoken_duration_s
```

Hard/structural checks:
- duração estimada total `<= 60s`;
- timecodes monotônicos, sem intervalos inválidos;
- hook aparece no início do roteiro;
- há separação entre fala, texto de tela e visual cue;
- script não é artigo truncado;
- source refs acompanham claims/números/entidades;
- grounding comum permanece hard gate.

Format-native diagnostics:
- speaking pace estimado versus configuração calibrada;
- claim load por janela de tempo;
- on-screen text overload;
- ausência de visual cue;
- excesso de jargão/fatos para o tempo disponível;
- conclusão abrupta/incompleta.

Failure codes sugeridos:
`VIDEO_OVER_60S`, `VIDEO_TIMECODE_INVALID`, `VIDEO_PACE_RISK`, `VIDEO_OVERLOAD`, `VIDEO_NO_VISUAL_PLAN`, `VIDEO_TRACE_MISSING`.

A duração pode ser estimada por palavras/ritmo ou, idealmente, por TTS/reading calibration. O único threshold congelado aqui é o requisito explícito `<=60s`; ritmo ideal permanece configurável até teste.

### 11. Fallback se chamada/modelo falhar ao vivo

Objetivo: manter demo honesta e demonstrável sem fingir sucesso do provider.

Estratégia em camadas:
1. **Primary** — executar chamada real no app.
2. **Prewarmed persisted run** — se provider falhar/timeout, abrir execução previamente produzida pelo mesmo pipeline, com banner `CACHED/PERSISTED RUN`, `run_id`, source hash e timestamp.
3. **Live evaluator on cached outputs** — reexecutar evaluator, source trace e telemetry localmente para continuar provando software real.
4. **Repair fallback** — se a chamada de repair falhar, abrir before/after persistido da mesma fixture, rotulado como persisted run, e reavaliar ambos live; não declarar que o repair aconteceu live.
5. **Parser fallback** — usar fixture local com texto + source map previamente extraídos, rotulada; a fonte original permanece disponível no preview.

Regra de credibilidade: nenhum fallback pode remover labels de estado, run id ou proveniência. Falha real deve aparecer como falha de provider, não como PASS fabricado.
