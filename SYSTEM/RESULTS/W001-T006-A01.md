## EXECUTIVE_SUMMARY

For this case, the architecture should be **a small explicit state graph, not an agent platform**. The recommended candidate is:

`parser boundary -> factual/anchor backbone -> LangGraph StateGraph -> 3x3 fan-out -> per-variant hybrid eval -> targeted repair only for failed variants -> aggregate/report`, with Pydantic models at I/O/domain boundaries, a persistent LangGraph checkpointer, and a thin Streamlit demo adapter.

Why this candidate: the case explicitly requires a graph with state, conditional refinement, 3x3 generation, auditability and cost/latency reporting. LangGraph currently exposes these primitives directly: typed/shared state, conditional edges, dynamic `Send` fan-out, reducers, per-node retry policies and checkpointers for fault tolerance. It therefore matches REQ-002/013 with less custom orchestration code than a hand-built engine.

`pydantic-graph` is a credible close alternative: its current V2 `GraphBuilder` supports typed state, decisions, spread/broadcast/fork and joins. However, the V2 migration documentation states that the builder API itself does not snapshot graph state; save/resume is handled elsewhere (for example Pydantic AI Harness `StepPersistence`), while Pydantic AI durable execution integrates with external engines such as Temporal, DBOS, Prefect, Restate and AWS Lambda durable functions. That is powerful, but is extra operational surface that is not justified for this demo unless a durability requirement beyond local checkpoint/resume appears.

A plain async Python state machine is the required simple counterfactual and emergency fallback. It is fastest to understand and can implement the same typed contracts, `asyncio` fan-out and targeted retry. But it weakens the explicit “workflow based on graph with state” requirement unless it is wrapped/exposed as a graph before final delivery. Therefore it should remain a baseline/fallback, not the default final architecture.

The UI should be **Streamlit for the case/demo**, with pipeline persistence outside Streamlit session state. FastAPI(+React) is preferable only if an external/multi-user API boundary becomes a real adoption requirement; Gradio is strong for model demos/queues but less natural than Streamlit for a dense 3x3 comparative dashboard with evaluator telemetry. The core pipeline must remain UI-agnostic so replacing Streamlit later is cheap.

### 3. Minimal candidate architecture

```text
Source PDF/text
  -> INGEST
  -> PARSE
  -> EXTRACT_ANCHORS
  -> VALIDATE_SOURCE
       | hard extraction failure -> FALLBACK/REVIEW (no generation)
       v
     FAN_OUT_3x3
       -> GENERATE_VARIANT x 9
       -> EVALUATE_VARIANT x 9
            | PASS -> ACCEPT_VARIANT
            | FAIL + repairable + attempts < cap -> TARGETED_REPAIR -> EVALUATE_VARIANT
            | FAIL critical/non-improving/cap -> REJECT_VARIANT
       -> AGGREGATE_MATRIX
       -> FINALIZE_TELEMETRY
       -> END
```

Principles:

1. **One factual backbone before nine narratives.** Parse/extract once, then fan out. Audience and format are orthogonal job dimensions.
2. **Immutable source lineage.** Repair can change generated content, not source anchors.
3. **Per-variant retry, not whole-run retry.** A failed beginner carousel must not regenerate eight valid variants.
4. **Separate transport failure from quality failure.** HTTP/provider errors use transport retry; evaluator failure uses targeted repair with diagnostics.
5. **Critical factuality is a hard gate.** A style/readability gain never compensates unsupported claims/numeric mismatches.
6. **Core is UI-agnostic.** UI submits a run and renders persisted results; it does not own durable workflow state.

### 4. Proposed typed state schema

Use a `TypedDict` or dataclass for LangGraph shared runtime state and Pydantic `BaseModel`s for validated domain/I/O boundaries. This keeps graph updates cheap while preserving strict validation at boundaries.

```python
RunState = {
  "run_id": str,
  "source_ref": str,
  "source_type": str,
  "parsed_document": ParsedDocument,
  "extraction": ExtractionReport,
  "anchors": AnchorSet,
  "jobs": list[VariantJob],                 # 3 audience x 3 format
  "outputs": dict[VariantId, VariantOutput],
  "evaluations": dict[VariantId, EvalReport],
  "repair_attempts": dict[VariantId, int],
  "errors": list[RunError],
  "telemetry": list[TelemetryEvent],
  "status": RunStatus,
}
```

Recommended domain contracts:

- `ParsedDocument`: normalized blocks with page/source span, tables or table references, extraction warnings.
- `Anchor`: typed fact (`number`, `date`, `entity`, `financial_term`, `condition/qualifier`, `quoted/source phrase`) + normalized value + source span/page.
- `AnchorSet`: anchors + coverage/confidence metadata.
- `VariantJob`: `{audience, format, job_id, prompt_version}`.
- `VariantOutput`: generated content + explicit source/anchor references.
- `EvalReport`: deterministic metrics + grounding findings + structured judge output + `hard_fail_reasons` + repair diagnostics.
- `TelemetryEvent`: run/job/node/attempt timing and usage data.

For parallel writes, outputs/evaluations/telemetry need merge/append reducers keyed by `job_id`; branches must not overwrite a shared scalar blob.

### 5. Parser / anchor extraction boundary

Parser reliability is upstream of all generation quality, so treat parsing as a **hard architectural boundary**, not a helper inside prompts.

```text
bytes/text -> ParserAdapter -> ParsedDocument -> AnchorExtractor -> AnchorSet -> SourceValidation
```

`ParserAdapter` contract should preserve page/source spans and report warnings. `SourceValidation` should compute at least:

- parse success;
- page/block coverage when measurable;
- critical numeric/date/entity anchor count;
- extraction warnings/table-loss indicators;
- anchor coverage/confidence.

If source validation falls below a calibrated floor or a critical table/number region is ambiguous, branch to a parser fallback/source preview/manual review. **Do not call the generator and hope the LLM reconstructs missing source facts.**

A-0008 therefore remains open: this task defines the boundary but does not claim that Copom, CVM facts and earnings releases have already passed parser tests. The build must test all three families.

### 6. Retry policy

Use three distinct policies.

**A. Transport/system retry**

- Scope: transient provider/network/database errors only.
- Mechanism: per-node retry policy with exponential backoff/jitter.
- Suggested initial cap: 3 attempts including the first call, then explicit failure/fallback.
- Do not retry deterministic validation errors as transport failures.

**B. Quality repair loop**

- Scope: generated output fails evaluator thresholds but source extraction is trustworthy.
- Repair input: original output + failed metrics + exact diagnostics + immutable source anchors.
- Suggested initial cap: at most 2 repair attempts per variant; calibrate later.
- Re-evaluate only the repaired variant.
- Stop early if the second attempt does not improve the failed dimensions or introduces a critical factuality regression.

**C. Source/parser failure**

- Scope: low extraction confidence, missing critical anchors, parser corruption.
- Action: no blind retry of generation. Switch parser/fallback or require review.

These caps are starting controls, not final evaluator thresholds; W001 calibration must validate them.

### 7. Minimal experiment executed

A framework-neutral async microexperiment modeled the exact 3x3 topology: 9 jobs execute in parallel; exactly 3 are forced to fail first-pass evaluation; repair succeeds on second attempt.

Two strategies were compared:

- **whole-matrix regeneration**: after any failure, regenerate all 9 outputs;
- **targeted repair**: regenerate only the 3 failed variants.

Observed synthetic orchestration result:

| Strategy | Generation calls | Unbounded concurrency wall time* | Concurrency cap=3 wall time* |
|---|---:|---:|---:|
| Targeted repair | 12 | ~20.8 ms | ~41.4 ms |
| Regenerate all | 18 | ~20.5 ms | ~61.1 ms |

`*` Each stub call sleeps 10 ms; this is **not** an LLM/provider benchmark.

Interpretation:

- targeted repair used **33.3% fewer generation calls** in the 3-failure scenario;
- with all calls able to run concurrently, both need two waves, so critical-path latency is nearly equal; the clear benefit is token/cost/load reduction;
- with a concurrency cap of 3, targeted repair also reduced synthetic wall time by ~32%;
- therefore architecture should instrument both cost and latency rather than assuming one implies the other.

Deterministic call-count sensitivity for one repair wave:

| First-pass failed variants | Regenerate-all calls | Targeted calls | Call reduction |
|---:|---:|---:|---:|
| 1 | 18 | 10 | 44.4% |
| 3 | 18 | 12 | 33.3% |
| 5 | 18 | 14 | 22.2% |
| 9 | 18 | 18 | 0% |

This directly supports RISK-0005 mitigation: repair should be branch-local and capped.

### 9. UI architecture trade-off

**Streamlit — recommended for W001/build demo**

Best fit for rapidly showing source preview, 3x3 matrix, metric cards, before/after repair and traceability in one Python app. Important boundary: Streamlit session/WebSocket state is not durable pipeline state, so run state must live in the graph/checkpointer/RunStore.

**FastAPI + separate frontend — defer**

Best when there is a proven external API, multi-client integration, independently deployed frontend or stricter service boundary. It increases demo implementation surface and does not itself improve evaluator quality. Keep the core package compatible so a FastAPI adapter can be added later without changing the workflow.

**Gradio — viable secondary option**

Excellent for model demos and built-in queueing/concurrency controls. It is less natural than Streamlit for a dense analysis/dashboard experience and its session state should likewise not be treated as workflow durability.

1. **Choose LangGraph StateGraph as the leading W001 orchestration candidate**, because it directly matches state graph, fan-out, conditional routing, retry and checkpoint requirements with limited custom infrastructure.
2. **Use Pydantic for domain/I/O contracts, not necessarily as the graph runtime state everywhere.** Prefer TypedDict/dataclass graph state when recursive validation is not needed on every update.
3. **Keep Pydantic Graph as the strongest alternative**, especially if the team values type-driven graph construction more than built-in checkpoint semantics. Do not add an external durable engine solely for this case demo.
4. **Separate transport retries from evaluator-driven repair** and cap both independently.
5. **Adopt targeted per-variant repair**; never regenerate the full 3x3 matrix because one branch failed.
6. **Make parser/anchor validation a pre-generation hard gate.**
7. **Use Streamlit as a thin case/demo UI**, with durable state outside the UI layer.
8. **Keep a plain async Python implementation as the baseline/fallback** and use it to detect framework overengineering.

## OVERENGINEERING KILL CRITERIA

Kill/defer a component when any of the following holds:

- LangGraph cannot pass a local smoke test showing 3x3 fan-out, one-branch failure, targeted repair and checkpoint/resume without substantial custom machinery; fall back to the simple engine while preserving contracts.
- A workflow feature adds complexity but does not improve a required metric, failure recovery, testability, auditability or demo clarity against the simple baseline.
- An external durable execution engine (Temporal/DBOS/Prefect/Restate/etc.) is needed only because a framework choice introduced it, not because the case/adoption requirements demand long-running cross-process workflows.
- FastAPI+separate frontend is proposed without a concrete external integration/multi-client requirement.
- GraphRAG is proposed only because “graph” appears in the case; the requirement is workflow state graph, not knowledge-graph retrieval.
- Multi-agent planner/debate is proposed without evidence that it improves calibrated output quality; it increases cost/latency/evaluation circularity.
- Retry count grows while failed metrics do not improve; stop repair, preserve diagnostics and surface failure instead of looping.
