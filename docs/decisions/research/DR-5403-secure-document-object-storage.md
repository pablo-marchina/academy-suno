# DR-5403 — Secure document/object storage and PDF ingestion lifecycle

`TASK_ID: W005-T004`
`ATTEMPT_ID: A01`
`RESEARCH_DATE: 2026-09-22`
`STATUS: CANDIDATE / NO_STORAGE_VENDOR_PREFERENCE`
`CONFIDENCE: HIGH for security lifecycle; MEDIUM for pooled-object-store candidate`

## 1. Decision question

How should Academy Suno accept, store, validate, process, serve and delete private PDF documents without exposing arbitrary server filesystem paths, cross-tenant objects or malicious document content?

## 2. Workload / constraints

The product ingests financial/source PDFs that become extracted evidence, runs and generated artifacts. PROD-004 requires controlled object storage, format/size/content validation, path/filename safety, source hash, provenance and retention policy. RISK-0032 marks arbitrary filesystem path/upload abuse as P0. Tenant isolation and observability redaction must also hold throughout the document lifecycle.

Exact file-size, page-count and retention-day thresholds are unknown and must not be invented.

## 3. Alternatives

### A. Server-local filesystem upload
Rejected as production default. It is difficult to share safely across replicas, invites path/filename hazards if exposed through user input and conflicts with durable shared storage requirements.

### B. Private pooled object store with application-generated tenant keys
All uploads land in a private bucket/container under application-generated opaque keys containing internal tenant/workspace identifiers. Access is mediated by the application or narrowly scoped, short-lived signed URLs.

### C. Bucket/container per tenant
Stronger resource-level separation and easier tenant-level policy/retention boundaries; higher provisioning/policy/observability burden as tenant count grows.

### D. API proxy for all upload/download bytes
Strong central authorization point and avoids bearer signed URLs at clients, but consumes application bandwidth/compute and can become a throughput bottleneck.

### E. Hybrid
Pooled private object storage by default, with dedicated bucket/container/encryption boundary for tenants whose policy requires it; API may stream especially sensitive downloads while normal transfers use signed grants.

## 4. Evaluation criteria

1. cross-tenant object access = 0 in defined tests;
2. no arbitrary filesystem path from untrusted input;
3. object key is generated by the server and bound to org/workspace/document record;
4. uploaded bytes cannot enter parser/workflow until validation is complete;
5. checksum/provenance is immutable and queryable;
6. malicious-content blast radius is bounded;
7. signed grants are least-privileged, short-lived and not logged;
8. object/derivative deletion and retention are auditable;
9. multi-replica/shared-storage compatibility;
10. provider portability and cost/operational burden.

## 7. Primary evidence first

OWASP and official provider documentation define the security pattern. The LGPD primary text constrains retention design but is not used to invent a fixed retention duration. No cloud vendor is preferred from documentation alone.

## 8. Security / reliability / cost / lock-in

### Candidate lifecycle

#### 1. Upload intent

Authenticated user calls an API operation such as `POST /workspaces/{workspace_id}/documents/uploads`.

The server:

- resolves the principal from the trusted session/token;
- loads workspace → organization binding from application storage;
- authorizes an explicit upload permission;
- creates `upload_id` / `document_id` and a server-generated opaque object key;
- records expected metadata (declared size/type, original display name only as sanitized metadata, optional expected checksum);
- returns a short-lived transfer grant or server-init upload session scoped only to that exact object and operation.

The client never supplies a server filesystem path and never chooses an authoritative tenant prefix.

Candidate key form:

```text
org/{organization_uuid}/workspace/{workspace_uuid}/uploads/{upload_uuid}/original.pdf
```

The visible original filename is metadata, not the storage identity.

#### 2. Quarantine landing

The object is private and lands in `QUARANTINED`. It is not readable by ordinary product users and cannot be consumed by the source parser/workflow.

#### 3. Validation / scanning

A least-privileged scanner performs defense-in-depth checks:

- required extension allowlist (`pdf` for this workflow);
- MIME/type signal + PDF signature/structure validation (neither is trusted alone);
- server-measured byte size and bounded resource consumption;
- SHA-256 or equivalent strong source digest stored in document provenance;
- safe parser/sandbox configuration with no outbound network access unless explicitly required;
- CPU/memory/time/page-budget enforcement derived from later workload evidence;
- antivirus/sandbox scanning where available;
- CDR for PDF where evidence/policy justifies it;
- reject or separately handle encrypted/password-protected documents until a secure supported flow exists;
- never execute embedded scripts/links or arbitrary external references as part of validation.

Exact numeric upload/page/time limits remain `PENDING_EVIDENCE`.

#### 4. Promotion

Only after validation succeeds does the document become `CLEAN/AVAILABLE` and a processing job is enqueued. The validated source hash, tenant/workspace IDs, scanner version/config and object version are bound to provenance.

A failed or timed-out scan transitions to `REJECTED` or `QUARANTINE_ERROR`; it never falls through to processing.

#### 5. Read/download

Every read begins with current application authorization. Delivery is either:

- API streaming, or
- a very short-lived, read-only signed URL/SAS scoped to the exact object.

Signed grants are bearer capabilities: do not place them in analytics events, trace attributes or normal logs. Raw object keys are not accepted from untrusted request bodies as authorization facts.

#### 6. Derivatives

Extracted text, page images, embeddings, chunks and generated artifacts inherit `organization_id`, `workspace_id`, `document_id`, source hash/provenance and retention class. Cache keys and queue payloads include stable tenant/resource identity.

#### 7. Retention/deletion

Represent policy explicitly instead of hard-coding a duration:

```text
retention_class
retention_expires_at
legal_hold
scheduled_delete_at
deleted_at
deletion_reason
```

Deletion must traverse source object + versions, derivatives, generated artifacts, indexes/embeddings and content-bearing telemetry where policy requires it. Backups follow a separately documented expiry/recovery model; deletion is not falsely claimed instantaneous in immutable backups.

LGPD supports purpose/necessity and treatment-end elimination principles but allows legal retention exceptions. The concrete Suno legal basis and retention calendar remain `PENDING_POLICY`.

### Least-privileged service split

- API/upload-intent service: metadata CRUD and ability to mint narrowly scoped upload/read grants; no broad object listing.
- scanner: quarantine read + validated-area write/status update only; no organization administration.
- workflow worker: read only CLEAN sources for its assigned tenant-bound job; write only its tenant-bound derivatives.
- observability exporter: metadata/metrics only by default, no raw document payload.
- CI/deployer: deploy permission without production document read permission.

### Telemetry redaction

Default logs/traces must not contain:

- raw PDF text or extracted sensitive source content;
- full prompts/outputs containing source content unless a separately governed capture mode is enabled;
- cookies/session IDs/JWTs/access tokens;
- signed URL/SAS query strings;
- secret keys/connection strings;
- unredacted personal data not required for the event.

Preferred telemetry: opaque internal IDs, source hash, content length/page count, status, scanner/parser version, latency/cost metrics and classified error codes.

### Reliability / cost / lock-in

Object storage is compatible with multiple replicas and decouples large binaries from the relational DB. Provider-specific egress/operation costs, malware-scanning integrations and retention features must be benchmarked after deployment candidates are known. Dedicated per-tenant containers remain an escalation path.

## 9. Reproducible benchmark / experiment

Implementation spike must use the same corpus across candidates:

- normal PDFs of small/medium/large representative sizes;
- wrong extension with PDF/non-PDF bytes;
- spoofed MIME;
- truncated/corrupt PDF;
- encrypted PDF;
- duplicate content with different filenames;
- traversal-like filenames (`../`, separators, reserved names) retained only as display-metadata test strings;
- oversized/resource-exhaustion fixture within safe test environment;
- scanner timeout/failure fixture;
- tenant A/B object-key substitution attempts.

Measure:

- unauthorized upload/read/delete successes (hard target `0`);
- quarantine bypasses to processing (hard target `0`);
- objects missing tenant + source-hash provenance (hard target `0`);
- public/raw unauthenticated object reads (hard target `0`);
- scan false accepts/false rejects on versioned fixtures;
- upload + validation p50/p95/p99 latency;
- storage/request/egress cost from measured bytes/operations;
- failure recovery/retry behavior.

No cloud-specific performance/cost benchmark was executed in A01; therefore no storage vendor is promoted.

## 10. Raw results + uncertainty

Security sources strongly converge on generated filenames, private storage, allowlisted types, content validation, size/resource limits and sandbox/scanning defense-in-depth. Major object stores expose scoped, expiring delegated-transfer mechanisms, so the lifecycle can remain provider-neutral.

Unknowns: maximum real document size/page count, acceptable scan latency, malware-scanner availability, data residency, legal retention, backup-retention constraints and cloud target.

## 11. Decision

`CANDIDATE`: private object storage with application-generated tenant-bound keys, quarantine → validate/scan → promote lifecycle, immutable source hash/provenance, and authorization-gated delivery.

`NO_STORAGE_VENDOR_PREFERENCE`.

Production API must remove arbitrary server filesystem path input. Local filesystem is allowed only as an isolated test/development implementation behind the same safe interface, never as the untrusted production contract.

## 12. Confidence

- Secure ingestion lifecycle: **HIGH**.
- Pooled object store default with dedicated isolation escape hatch: **MEDIUM-HIGH**.
- Specific storage/scanner provider: **LOW / no preference** until deployment and corpus bakeoff.

## 13. Reversal conditions

Reopen if:

- policy requires dedicated per-tenant storage/encryption boundaries;
- measured signed-URL threat/egress economics favor API streaming for the target workload;
- document parsing requires safe features incompatible with the quarantine sandbox;
- target cloud/service has materially stronger/weaker delegated-access primitives;
- legal retention/residency requirements force different storage topology.
